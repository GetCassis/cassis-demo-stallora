# Cassis Context Design Guide

This is the canonical guide to modeling a Cassis context well. It is written for
whoever edits the context (a person or an AI agent) working in the project's
git repository. The rules here are not style preference: they follow from **how
the text-to-SQL agent actually reads the context**, so breaking them produces
wrong SQL, not just messy files.

Read this before proposing a context change.

---

## 1. What a Cassis context is

The context is the curated business knowledge the agent uses to translate a
natural-language question into SQL. It has five kinds of object plus a project-level root context, edited as
files under the repository's context directory (`cassis/` by default),
with domains as Markdown and everything else as YAML:

| Layer | What it is | Key fields |
|---|---|---|
| **Root context** (`domains/README.md` body) | One free-text block, always in the agent's prompt | markdown |
| **Domains** | A navigable tree grouping the business by subject area | `path`, `display_name`, `description`, `context_md` |
| **Tables** | A physical warehouse table (introspected) or a virtual one (SQL-defined) placed in a domain | `name` (`schema.TABLE`), `description`, `synonyms`, `grain`, columns |
| **Columns** | Enrichment on a table's columns | `description`, `unit`, `synonyms`, `enum_values` |
| **Joins** | A known way two tables relate | `from_schema`/`from_table`, `to_schema`/`to_table`, `column_pairs`, `condition_sql`, `cardinality`, `description` |
| **Metrics** | A reusable business measure | `name`, `display_name`, `expression`, `table_schema`/`table_name`, `filters`, `unit`, `synonyms`, `notes`, `precomputed_in` |

On disk, the export layout is fixed: create each object in its canonical home
(`cassis context fmt` normalizes drift, but start in the right place):

```
cassis/                          (the git-sync base path)
  project.yml                    project identity: project id + Cassis format version (written by publish / pull)
  domains/README.md              root domain (path ""): frontmatter (type/title/description) + context_md body
  domains/<path>/README.md       one per sub-domain, nested by path (same Markdown format)
  tables/<schema>/<table>.yml    one per table, columns inline (YAML)
  metrics/<name>.yml             one per metric (YAML)
  joins.yml                      ALL joins, one list in one file (YAML)
```

Joins and metrics are never embedded inside a table's file, and a table's file
never carries keys the schema doesn't define — unknown keys are dropped at sync
time (run `cassis context fmt` to see what would be lost).

The **published** context is an immutable numbered snapshot: what production
answers from. The **unpublished** context is the editable state (the published
base plus unpublished changes). In a git-synced project the repository *is* the
edit surface: you edit the files, open a pull request, and merging syncs and
publishes it.

Physical tables and their columns come from schema introspection — you never
invent them; you *enrich* them (place them in a domain, describe them, set units,
synonyms and stored values). The one exception is a virtual table, which you define with a
`sql` body (see §5).

The one governing principle everything below serves:

> **Each fact lives in exactly one place, at the most specific layer that fully
> owns it. Never duplicate across layers. Never hand-write what the agent already
> reads automatically.**

## 2. How the agent reads your context

The agent has no other ground truth. It does not see the warehouse, the dbt
project, or the raw schema: only the strings in the context, with one fallback.
Where a physical table or column has no `description`, the agent reads the
warehouse's own comment on it instead (a `COMMENT ON`, a BigQuery description,
or a dbt description written to the warehouse by `persist_docs`), marked as
coming from the warehouse. A `description` you write always wins, and replaces
the comment entirely. A published version keeps the comments as they were when
it was published; a corrected comment reaches production at the next publish.
If a fact isn't in the context or in that comment, it doesn't exist for the
agent; if a string contradicts the data, the agent confidently writes wrong
SQL. Three mechanics drive every rule that follows.

**Retrieval is structured and automatic.** The agent navigates the domain tree
with a `get(path)` call and inspects a table with `get_table("schema.TABLE")`.
These assemble structured fields for free:

- `get(path)` returns the domain's `context_md` **plus** its direct sub-domains,
  each table (`name`, the **first sentence** of its `description`, `synonyms`,
  `grain`), and each metric (full definition). Opening a sub-domain brings its
  parents' pages with it.
- `get_table("schema.TABLE")` returns the table's full `description`, its
  columns, `grain`, and its **joins** (each with its condition, cardinality, and
  description). The agent opens every table before it queries it.
- The **root** domain (its `root_context`, root tables, root metrics) and the
  list of domains, each with its `path`, `display_name` and `description`, are
  in the prompt of every conversation.

Because those fields are surfaced automatically, **restating them in prose is
pure redundancy**, and redundant copies drift, which is how the context starts
lying to the agent. `context_md` and `description` are for the connective tissue
the structured fields can't carry, nothing the fields already carry.

**What is in front of the agent decides where a fact is seen:**

- *Choosing a domain*: the root context and each domain's `description`.
- *Choosing a table*: the pages it opened, their parents, and the first
  sentence of each table listed there.
- *Writing SQL on a table*: everything on that table (full description, every
  column, every join). Its domain's page too when the agent came through that
  domain, which is usual but not certain: a join or a mention can lead it to a
  table of a domain it never opened.

So what the agent needs to **choose** goes where it chooses (a domain
`description`, a table's first sentence, a page's routing), and what it needs to
**use** a table goes on the table and its columns, where it is always read.
Neither needs a copy at the other place.

**Minimum tokens to answer.** Every byte the agent reads costs tokens, and a
real context does not fit in the prompt at once: it is retrieved piecemeal.
Keep free-text fields concise; don't state what the object's own name already
makes obvious; watch your largest tables, since column count drives rendered
cost.

**Vocabulary in prose fields is the only vocabulary the agent has.** In prose
fields (descriptions, `context_md`, root context) refer to tables by their
`schema.TABLE` name as it appears in the context, never by some other alias the agent can't map back.
In SQL-bearing fields (a metric's `expression`/`filters`, a virtual table's
`sql`, a join's `condition_sql`) use real physical identifiers — those are SQL
and must match the warehouse (see §7).

## 3. The placement contract

Put each fact at the lowest layer that fully owns it:

```
column enum_values / synonym / description   single-column facts: stored values, meaning, encoding, unit, date format, nulls
  → table description                    single-table facts: scope, mandatory filters, "use this not that"
    → domain context_md                  cross-table routing, disambiguation, vocabulary spanning tables
      → root context                     truly global rules only: corporate identity, entity hierarchy, global conventions
```

Plus two non-prose homes that pull facts *out* of prose entirely:

- A **recurring calculation that encodes a business rule** → a **metric**, not a
  sentence.
- **How two tables relate** → a **join**, not a "joins to X on Y" note.

A fact written one layer too high is redundant (the tool already surfaces the
lower layer) or stranded where the agent won't look. A fact written one layer too
low can't express the cross-object relationship it's really about. The test for
`context_md`: imagine pushing the fact one domain level deeper — if that would
force you to copy it across sibling sub-domains, it belongs at this shared level;
otherwise push it down.

**When two places seem to need the same fact**, one owns it and the other holds
nothing, or a pointer:

| The fact | Lives on | The other place |
|---|---|---|
| How to use one table: scope, mandatory filter, trap | the table `description` | its domain page says which question the table answers, not the rule |
| What one column means or how it is encoded | the column | nothing on the table `description` or the page |
| A rule involving several columns, or which rows the table holds | the table `description` | nothing on the columns |
| A rule or term spanning tables | the deepest domain page covering them | nothing on the tables, nothing on sub-domain pages (read with their parents) |
| A convention true almost everywhere | the root context | nothing anywhere: it is in every prompt |

A **pointer** names where a fact lives and what it is about, never what it says:
"Refund rules: `billing.refunds`", or a link to the owning domain
(`[refunds](billing/refunds)`). If it must carry the rule to be useful, it is a
copy. Write one only where the agent would not otherwise look: prose that sends
it to a table or metric of **another** domain names it and links that domain, so
the page holding its rules is opened too. Objects read together need none: a
table and its columns, a page and its own tables and metrics, a sub-domain and
its parents.

**Never restate the structured fields:**

- Direct sub-domains are surfaced with their descriptions → no "Sub-domains: …"
  lists. If a child reads too thin to stand alone, fix its `description`; don't
  re-list it in the parent.
- Tables are listed with their first sentence, synonyms, grain → no `## Tables` block.
  Per-table facts go on that table's `description`; keep only genuinely
  cross-table routing in `context_md`.
- Metrics are surfaced with their full definition → don't re-paste a formula in
  prose, and that includes the metric's **own** `description` and `notes` (§8).
  Point to a metric by name **only** when it lives in a *different* domain
  than the prose discussing it; a domain's own metrics are surfaced alongside its
  `context_md` already.
- Joins are surfaced with their condition and cardinality → don't enumerate join
  keys in prose. The only join content that belongs in prose is a join+filter
  *recipe* no single structured join can express.

**Short or empty beats redundant.** When the structured fields already say
everything worth saying, leave the prose field short or empty. An empty
description costs nothing; a redundant one goes stale.

## 4. Domains and `context_md`

Build a domain hierarchy that mirrors **how the business thinks about its data**,
not the raw schema layout. Nest as deep as the structure genuinely warrants
(there is no level cap), but don't add a level that carries no distinct context of
its own — an empty navigational domain is just noise. Every table and every
metric names a `domain_path` that must resolve to a domain you've declared (or the
root, `""`).

Each domain is a Markdown file (`domains/<path>/README.md`, or `domains/README.md`
for the root). Its YAML frontmatter holds the structured fields — `type: Domain`,
`title:` (the display name), `description:`, optionally `owners:` — and the
Markdown body **is** the domain's `context_md`. Write the display name as `title`,
not `display_name`: an unrecognized frontmatter key is rejected by
`cassis context check` and on sync.

`owners:` lists who the domain's issues are routed to. Each entry is an email
address (one person) or a typed reference to a group or account in another tool:
`slack:@group` for a Slack user group, `github:@user` or `github:@org/team` for
GitHub. Anything else is rejected, a bare `@name` included.

```yaml
owners:
- jane@acme.com
- slack:@finance-data
- github:@acme/finance-data
```

A domain without `owners` inherits its nearest parent's; the root's are the
default. Owners are routing only: they grant no edit permission and the agent
never sees them. Cassis does not resolve an entry to people: an issue carries
all of its domain's owners as declared, and whatever reads the issue uses the
types it understands.

A useful convention inside `context_md`: a `## Terms` section for the domain's
vocabulary and disambiguation, and a `## Notes` section for routing hints and
scope caveats. Omit either if you have nothing for it.

`context_md` carries only the connective tissue the structured fields can't:

- **Cross-table routing and disambiguation** — which table answers which
  question; "two different 'active users'" and which to use when.
- **Business rules, scope and temporal caveats, aggregation traps** that span
  more than one object.
- **Vocabulary / glossary** that maps to no single table (acronyms, internal
  project names, business terms).
- A short **orientation paragraph** for a navigational domain.
- Markdown **links** to related domains, using the resolvable domain path
  (`[berries](play/features/berries)`), not a bare filename.

**Root context** — the body of the root domain (`domains/README.md`), injected into every
conversation — **holds only what applies across almost every query:** corporate
identity, the core entity hierarchy (how the central models relate — e.g. "users
belong to companies via enrollments; primary enrollments are employees, partner
and child are dependents"), global country/timestamp/currency conventions,
default population exclusions, and cross-cutting vocabulary that maps to no single
domain. Everything domain-specific moves down.

## 5. Tables

A table's `description` answers *"what is this, and what must the SQL agent know
to use it correctly?"* — business meaning **plus** the correctness facts (scope,
mandatory filters, gotchas). The grain goes in the `grain` field — the identifying
column(s) — not in the description: the agent reads it structurally, and "one row
per order" or a `Grain:` line in prose is a second copy. Say what a row is only
when the grain columns don't show it. Don't enumerate the columns either — the
column list is surfaced automatically.

**The first sentence is what the table is chosen by.** A domain page lists each
table with the first sentence of its description only, cut when long. Keep it
under 160 characters; make it say what the table is and, where a sibling could
be mistaken for it, when to use this one. The rest is read once the table is
opened: it holds the rules for using the table, and the page does not repeat
them.

Use `synonyms` for alternate names a user might say ("purchases", "transactions"),
never an "also known as" sentence in the description.

When a table's rows have non-obvious semantics, put the rule in the description:
a table that keeps one row per entity chosen by a priority ordering, a
`GROUPING SETS` table whose discriminator column must be filtered to avoid
double-counting, a JSON/array column and how to query it. Don't silently omit a
messy column — surface it with guidance.

**Virtual tables are a last resort — almost never the right answer.** A virtual
table is a `sql`-defined `SELECT` placed in the context. Do **not** reach for one
to hold a single field, a metric, or a simple rollup: use a **metric** for a
recurring calculation, a **column** description to clarify a field, a **join** to
relate two tables, or **enrich an existing physical table**. A virtual table is
justified only when a genuinely complex object cannot be represented by any
physical table — e.g. extracting structured rows out of a nested JSON/blob
column, or reshaping an entity split across an unusable physical layout. When you
do create one, prefer selecting from existing physical tables (don't duplicate a
fact table), list its columns so they can be enriched, and quote/case identifiers
in the `sql` per §7.

## 6. Columns

Column enrichment is `description`, `unit`, `synonyms` and `enum_values` — you
cannot add or rename columns (they come from introspection). The agent sees a
column's name, type, `unit`, `synonyms` and `enum_values` structurally; the
`description` carries what those don't: meaning, encoding, date format, null
behavior, any mandatory filter.

- **Stored values go in `enum_values`, not in the description.** A categorical
  column with a small, stable set (a status, type, tier, code) lists every value
  it stores in `enum_values`, verbatim and case-exact, in a meaningful order
  (ordinal sets keep their order). A value's meaning goes in that value's own
  `description`; the column `description` says what the column *means* and never
  lists values. Free text, identifiers and high-cardinality columns get no
  `enum_values`; a few notable codes in a large column stay in the description.
  How to get the list right, and what to do with value lists already written in
  prose, is §10.

  ```yaml
  columns:
  - description: Lifecycle stage of the subscription.
    enum_values:
    - value: ACTIVE
    - value: CANCELLED
      description: Cancelled by the customer; access runs to period end.
    name: status
  ```

- **Prioritize the trap columns.** Disambiguate similarly-named columns
  (`created_at` vs `updated_at`, `amount` vs `net_amount`), numeric-encoded
  columns, numbers-that-are-timestamps, dates-stored-as-text. Skip the
  self-explanatory ones — a description that just restates the column name is
  wasted tokens.
- **Set `unit`** whenever a number is a currency, percentage, or duration —
  aggregation correctness depends on it.
- **Use `synonyms`** for 1–3 short, plain alternate terms a user might use.
- **Don't copy the warehouse comment.** A column or table whose warehouse
  comment already tells the agent what it needs can stay without a
  `description`: the agent reads the comment (§2). Write a `description` when
  the comment is missing, wrong, or misses a trap; it then replaces the comment,
  so carry over whatever in the comment still holds.
- **Facts, not SQL.** Say what the column holds and how it is encoded ("TRUE =
  the account can sign in"), never a fragment to paste ("filter with
  `is_active = TRUE`", "count people with `COUNT(DISTINCT id)`"). Writing the SQL
  is the agent's job.
- **Relationships live in joins.** A foreign-key column says what it identifies
  ("the owning organization"), not which table it references or on what
  condition; the join carries that, and a description repeating it drifts when
  the join changes. No "points at …", "join to … on …" or "FK to …": if the
  relationship has no join yet, add the join.
- **Keep the join key queryable.** A foreign-key column stays a real, described
  column even when a join covers the relationship — hiding it leaves the agent
  unable to filter or group on it without traversing the join. Test: imagine a
  question that filters or groups by this column *directly*. If you can, describe
  it; if the column only ever appears via the join, it needs less attention.

## 7. Joins

All joins live in the single `joins.yml` file, one list entry per join. An entry
names its two endpoints with schema and table split into separate keys, carries
the joined column pairs, and the `condition_sql` — the ON-clause boolean
expression, with every column table-qualified and quoted in the warehouse
dialect. Set `cardinality` (`one_to_one` / `one_to_many` / `many_to_one` /
`many_to_many`, read from the `from` side to the `to` side) and say what the
relationship means in `description`:

```yaml
- from_schema: public
  from_table: orders
  to_schema: public
  to_table: customers
  column_pairs:
  - from_column: customer_id
    to_column: id
  condition_sql: '"public"."orders"."customer_id" = "public"."customers"."id"'
  cardinality: many_to_one
  description: The customer who placed the order.
```

Fill in both `column_pairs` and `condition_sql` — the agent is shown both.

- Cover every foreign key and every obvious `*_id` reference between tables. FK
  joins are pre-seeded from introspection — confirm them; then add the ones the
  heuristic missed (columns whose names diverge across the two tables, or
  relationships that go through a bridge table).
- **The `description` is the business meaning of the relationship**, in a
  sentence, plus any trap specific to this pair of tables. It is not the
  condition or the cardinality in words ("links orders to customers on
  customer_id = id", "each order has exactly one customer"), and not a fact
  about one endpoint (its grain, the type of its key): that fact lives on that
  table or column once, however many joins reach it. A composite key or a cast
  is already in `column_pairs` and `condition_sql`. When the fields say it all,
  leave the description empty.
- **Join forms:** a simple join is a single-column equality
  (`a.x = b.y`); a **composite** join ANDs the equalities
  (`a.x = b.x AND a.y = b.y`); a **filtered** join ANDs a filter
  (`a.x = b.y AND b.type = 'order'`); a **functional** join uses a function
  (`DATE_TRUNC('day', b.ts) = a.day`).
- **Avoid join explosion — the single biggest failure mode.** A column shared by
  many tables (`country_id`) must **not** get a join between every pair; it
  degrades agent quality badly. Pick one hub table for a shared key and link the
  peers to it (hub-and-spoke). Coincidental column-name matches — two unrelated
  tables that both happen to have a `contract_id` — get **no** join.

## 8. Metrics

Define a metric when a calculation **recurs and encodes a business rule** — e.g.
revenue net of refunds, active-user counts with a specific definition. Don't turn
every column into a metric.

- `expression` is the **aggregation expression only** (`SUM(net_amount)`,
  `COUNT(DISTINCT customer_id)`), never a full `SELECT`.
- `table_schema` + `table_name` name the base table it aggregates over (omit
  only for a genuinely cross-table metric).
- `filters` is any mandatory `WHERE` condition always applied
  (`status <> 'cancelled'`).
- `unit` for non-obvious result quantities; `synonyms` for alternate names;
  `precomputed_in` the `schema.TABLE` of a rollup that already materializes it, if
  one exists.

One file per metric under `metrics/<name>.yml`:

```yaml
name: net_revenue
display_name: Net Revenue
domain_path: sales
table_schema: public
table_name: orders
expression: SUM(amount_cents - refunded_cents)
filters: status NOT IN ('cancelled', 'refunded')
unit: euro cents
synonyms:
- net sales
- revenue net of refunds
description: Revenue kept after refunds; the top-line sales figure.
```

A metric definition beats a prose "revenue = net revenue excluding tax" note —
the metric is surfaced structurally and can be reused; the prose drifts.

**Definition in the fields, meaning in the prose.** `expression`, `filters`,
`table_schema`/`table_name` and `unit` *are* the definition. Every prose field —
including the metric's own `description` and `notes` — says what the number means
and when to use it, never how it is computed: no columns, thresholds, time windows,
or numerator/denominator. A rule copied into prose is a second definition, and the
two drift apart (one metric shipped with a 90-day window in `filters` and "30 days"
in its own description). Business intent is fine ("draft bookings are not
commitments"); its encoding (`status <> 'DRAFT'`) is not. This holds even when the
metric's name *is* the term being defined ("active partners"): the reader sees
`filters` right next to the description. Disambiguate from sibling metrics by the
question each answers, never by restating their windows or filters. If the fields
say it all, keep the description to a phrase or leave it empty.

```yaml
# Bad — restates the definition
description: Active partners = COUNT(DISTINCT partner_id) with a non-cancelled
  booking in the last 90 days.
# Good — what the number is for
description: Partners still trading; the activity count used for outreach targets.
```

## 9. Identifiers and case — where SQL silently breaks

A stored `name` on a table or column is a **physical identifier**, not a display
string. The SQL agent quotes every identifier to preserve case
(`"schema"."table"."column"`), and quoted identifiers are **case-sensitive** in
Snowflake and Postgres. So the context's stored identifier case **must equal the
warehouse's stored case**, or generated SQL fails with errors like
`Schema "core" does not exist`.

- Seed the physical layer from schema introspection, which returns the real case
  (Snowflake unquoted DDL is stored UPPERCASE; Postgres lowercase). Never
  hand-lowercase identifiers from a spreadsheet and import them.
- This applies to **identifiers only**: `schema_name`/`table_name`, column `name`,
  `grain`, join endpoints (`from_schema`/`from_table`/…), `column_pairs` and
  `condition_sql`, and metric `table_schema`/`table_name`/`expression`/`filters`. Logical fields — domain paths, display names, descriptions,
  **synonyms**, `context_md` — stay natural language; the matching layer there is
  case-insensitive and should read naturally. A column's `enum_values` are data
  literals, not identifiers, but they are matched exactly too: write each value
  as stored, case included.
- **Schema-qualify everything.** Table references in SQL and prose carry the
  `schema.TABLE` form (`dbt_core.fct_orders`), so a scope rule about `raw.users`
  never accidentally catches `core.users`, and a prefix that doesn't match what
  the warehouse actually has doesn't silently resolve to nothing.

## 10. Examples and enums — handle like loaded weapons

An inaccurate example primes the agent **more strongly** than a correct prose
description, so a wrong example is worse than none.

- **`enum_values` is the complete set of stored values, verbatim.** The agent
  treats it as closed: filter literals come from it, exact case, and a value it
  doesn't list does not exist. Verify the set against the source before writing
  it — a `SELECT DISTINCT` over the column, or a `CHECK ... IN (...)` constraint
  the schema shows — and write it plainly, with no "observed so far" hedge and no
  counts. If you don't have the exact set, leave `enum_values` out rather than
  approximate it: a partial list is worse than none, because the agent stops
  looking for other values. When two columns supposedly share an enum, verify
  they're identical before encoding both.
- **Move value lists out of prose.** Older descriptions list values in text
  ("Possible values: …", "Values:", "One of:", "Stored values: 'EDITOR'"). When
  you touch a table and find one, move the list into that column's `enum_values`
  and delete it from the description in the same change, verifying it against
  the source first when you can. A hedged or open-ended prose list ("etc.",
  "includes", "e.g.", "and legacy …") is **not** the complete set: verify it, or
  drop it without promoting it. Never turn an approximation into `enum_values`.
- **Be wary of analogies to external products** — they mislead the moment the
  real mechanic diverges.
- **Don't describe things that don't exist.** Every table, column, and value you
  reference must be real.
- **A hedge is not a safeguard.** "Likely `'M:SS.mmm'`", "probably", "appears to
  be" reach the agent as the claim itself; the qualifier does not survive into
  its reasoning. If a storage format, a unit, or a reason for nullability is not
  in the source, leave it out and record the open question instead.
- **Never invent a contrast with a column you did not read.** When a new column
  shares a name with one on another table (`position_order`, `status_id`,
  `lap`), the tempting sentence is "here it means X, unlike there". A schema
  dump cannot support that. Open the sibling's description and reuse it if it
  applies; if you can't confirm the relationship, say it's unverified. A false
  distinction drawn confidently survives review as a documented decision.

## 11. Cross-cutting disciplines

- **One home, then de-duplicate.** When you learn a fact, put it in exactly one
  place — the most specific layer that owns it — and, if the same fact already
  appears elsewhere, remove the copy or leave a one-line pointer. When a
  stakeholder clarifies something, scan every layer for places that need the
  update and land it in only one.
- **Rewrite, don't append.** When you learn more about an object, rewrite its
  text as one description. A second layer added under the first (`Notes:`,
  `Caveats:`, `Update:`) states the same fact twice, and the next editor updates
  only one.
- **Work back to the source, not a derived copy.** Model from the warehouse
  schema and the authoritative source SQL, not from a previously-written
  description. Each derivation loses information; chaining them compounds the
  loss. Where sources disagree, pick one authoritative source and document why it
  wins.
- **Scope every edit to what was asked.** Don't bundle unrequested companion
  changes (extra metrics, synonyms, reorganizations) into a change. When you spot
  an adjacent improvement, note it and let a human opt in. The one exception: a
  metric you place in a *different* domain than the prose that discusses it takes
  a one-line pointer in that prose, as part of the same change.
- **Ground writes in the real schema.** Before referencing a physical table or
  column, confirm it exists. Don't invent tables or columns; the physical schema
  is fixed.
- **Never persist a measurement.** Prose holds stable encodings and business
  definitions, not what the data shows today. Row counts, distinct counts, shares,
  distributions, funnel rates and "as of" / "currently" / "observed" statements go
  stale silently, and the answering agent repeats them as fact. Query the data to
  *verify* a stable fact (a column's stored values, a date format, null
  behaviour) and write only the fact: the values in `enum_values`, not "only
  'EDITOR' observed (6 of 6, 100%)" in prose. Complete value sets and constants
  the business fixes (a 14-day trial) are facts, not measurements.
- **Ask for the business meaning; don't guess.** A term like "active user" or
  "last month" has a project-specific definition (time window, criteria, filters).
  Encode the business's actual definition, not a textbook default.

---

## 12. Extension passes: structure before content

Adding a source or a whole subject area inverts the scoping bullet above. §11 is
written for maintenance edits, where a structural change is genuinely adjacent;
on an extension pass the tree *is* the change — every table and metric names a
`domain_path`, so content filled into a hierarchy you already doubt all has to
move. Same human opt-in, front-loaded:

1. **Scope.** Agree what is being added, from which sources, in what order.
2. **Structure.** Evaluate the existing hierarchy against what is arriving and
   propose the tree changes — new domains, splits, moves — for approval *before*
   any content. On approval, create the new domain files frontmatter-only (empty
   body), so every `domain_path` resolves while you fill.
3. **Fill bottom-up.** Column and table facts, then metrics and joins, then each
   domain README body last, written from what is left over. That residue is by
   construction the cross-table connective tissue domain level owns, so the order
   enforces the one-home rule instead of leaving it to vigilance. Bottom-up is an
   authoring order, not a holding rule: a fact learned out of order still lands at
   its owning layer immediately (§11). If filling shows the approved tree is wrong
   — a domain overloads, or wants to split — stop and return to 2 rather than keep
   filling into it.
4. **Guard.** Each new domain gets at least one eval case, added before you open
   the pull request: a question it answers, probed and kept as in §13. `cassis
   context check` names the new domains and changed tables no case reads yet.

## 13. Working in a git-synced repo

The repository is the source of truth. Edit the files, then verify before opening
a pull request: the CLI runs the same checks the platform does, from your
checkout:

- `cassis context check`: validate the files (parse, round-trip, semantic
  checks); the same gate that runs on the pull request.
- `cassis context fmt`: rewrite the files in canonical form, so hand or agent
  edits round-trip cleanly and any dropped/unknown fields become visible in the
  diff before you commit.
- `cassis context test -q "…"`: run a real question through the text-to-SQL
  agent against your local files, to confirm a change actually *works* (e.g. a new
  column gets picked), not just that it validates.
- `cassis eval run`: score the project's eval suite against your local files to
  check the change for regressions before merging. `--changed` runs only the
  cases the change affects, and names what no case covers.
- Keep a guard: add an eval case for the question before you open the pull
  request; Cassis checks it once the change is published. Every fix and every
  new coverage gets one. `cassis context test -q "…" --save-case` keeps a
  successful probe as a case (probing again updates it); `cassis eval add-case
  --pending-change` adds one by hand. Until the change is published the case
  is pending: other runs list it but count no verdict on it. A question the
  agent has to ask a clarification about is no guard: write it with the detail
  it lacks and probe it again.

Merging the pull request syncs and publishes the context; nothing reaches
production answers until then.

When the change fixes Cassis issues, say so in the pull request instead of
closing them by hand. Write one mention per issue in the PR description:
`Resolves <id>` (the full id, or its first 13 characters or more; `Closes` and
`Fixes` are accepted too). `cassis issues show <id>` prints the exact line to
copy, as `PR mention:`. Cassis resolves each mentioned issue when the pull
request merges and the context is published, and records the pull request on
the issue, so the resolution carries the change that earned it. Guard each
fixed issue with a case for the question users were failing on: `get_issue`
over MCP names those questions, and passing the issue (`--issue <id>`, or
`issue_id` over MCP) makes the case wait for that issue's resolution, the
publication that carries the fix.

Resolving by hand is for outcomes that never go through a pull request:
`cassis issues resolve <id>`, or `update_issue_status` over MCP. It needs the
editor or admin role, changes no context, and belongs to whoever owns the
project. Confirm first that the published version really contains the fix
(`cassis status`, or `get_project_status`). Never resolve before publication,
and never silently: an issue nobody resolves stays in the triage queue and
reads as a gap that was never fixed.
